# Selected desktop workflow and recovery

Only the selected checkbox workflow has an implemented durable recovery helper: `CheckboxRecovery(executor, directory)` in `src/troubleshoot/desktop/recovery.py`. Its native integration is not enabled in the API automatically. Member 3 must wire this wrapper, approvals, startup inspection and original-symptom checks before enabling it for users.

`apply(snapshot, {control_id, state}, context)` durably records the exact target (handle/PID/start), control ID/name, original binary state and proposed state before input. It invokes the existing authoritative executor, which enforces current geometry/identity/freshness and action-specific approval. An uncertain outcome retains the record. A pending record blocks another mutation. Records belong to that Windows machine/session, never to a remote inference host.

`restore(recovery_id, new_context)` freshly observes the same target/control. If already at the original state, it records baseline restoration without input. Otherwise it only offers restoration if the checkbox is still at the expected changed state. Replacement controls, third states, missing windows or inspection failures retain the record and require manual inspection. Restoration uses a new approval, then native postcondition verification; only verified restoration deletes the record. No stale token or automatic generic undo is used. No attempt is made to restore unrelated settings, external side effects or unsaved application data.

The directory must be session-owned/private and writes serialized by the integrating runtime; this helper does not implement an API session lock or cross-process journal lock. Local files are trusted executor state, not model input. Do not expose the directory or allow model-generated recovery paths. Crashed/interrupted startup requires inspection of pending records before any new desktop workflow; do not automatically replay them.

Mouse delivery and graceful close currently have **no semantic recovery guarantee**. Keep these disabled for user-facing repairs until each chosen application workflow has a baseline, an independently measurable original symptom, and an approved recovery method. The existing native tools are controller primitives; their presence in a registry does not approve every workflow. A disposable synthetic fixture can be cooperatively closed and freshly recreated; that is test recovery, not recovery of user documents.

Fresh tests cover durable restore, uncertain input, pending records, replacement controls, missing approval, already-restored state, intervening indeterminate state and persistence failure. Native guest tests separately demonstrated checkbox Off → On → independently verified feature state → Off, followed by fixture cleanup. The Python journal and API flow were not executed in the guest (guest Python is unavailable).
